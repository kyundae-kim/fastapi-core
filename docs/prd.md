# fastapi-core 제품 요구사항 정의서 (PRD)

> 문서 리비전: 2026-08-02
>
> 기준 릴리스: `fastapi-core 0.6.0`
>
> 상태: current-implementation
>
> 문서 원칙: 제품 가치와 capability를 정의하며, 구체적인 심벌·경로·스키마 계약은 SRS에서 관리한다.

---

## 1. 제품 개요

### 1.1 제품 정의

`fastapi-core`는 **DocMesh Py Core 기반 서비스를 FastAPI로 실행하고 노출하기 위한 공통 컴포넌트**다. 외부 시스템 연결 기능을 단순 재노출하는 SDK가 아니라, 서비스 팀이 공통 웹 계층과 운영 기반을 반복 구현하지 않고 도메인 API 개발에 집중하도록 애플리케이션 조립, 보안, 운영 상태, 자원 수명주기 및 오류 계약을 제공한다.

### 1.2 배경과 문제

- 서비스마다 애플리케이션 초기화, middleware, 공통 router 및 외부 의존성 연결을 다시 구현하면 개발 비용과 동작 편차가 커진다.
- 인증·인가, 오류 응답 및 요청 추적 정책이 서비스별로 달라지면 보안성과 장애 분석 가능성이 낮아진다.
- 외부 서비스와 서비스 고유 자원의 생성·상태 점검·종료가 애플리케이션 수명주기와 분리되면 부분 초기화, 정리 누락 및 준비 상태 오판이 발생할 수 있다.
- 필수·선택 의존성과 대체 가능한 서비스 구성이 기동 전에 검증되지 않으면 잘못 조립된 애플리케이션이 실행될 수 있다.
- 공통 컴포넌트의 업그레이드 시 소비 서비스가 기대하는 앱·인증·헬스 계약의 회귀 여부를 확인하기 어렵다.

### 1.3 대상 사용자

- DocMesh Py Core 기반 API를 개발하는 백엔드 개발자
- 여러 FastAPI 서비스를 표준화하는 플랫폼 개발자
- 서비스의 생존·준비 상태와 장애 원인을 확인하는 운영자
- 공통 컴포넌트 버전 업그레이드의 호환성을 검증하는 소비 서비스 팀

## 2. 목표와 비목표

### 2.1 목표

- **G-001. 일관된 앱 조립**: 서비스가 공통 애플리케이션 조립 경로로 웹 계층, middleware, router 및 수명주기를 구성할 수 있어야 한다.
- **G-002. 안전한 기본값**: 외부 서비스와 인증 기능은 명시적으로 선택하며, 기본 애플리케이션은 별도 인프라 없이 기동·상태 확인이 가능해야 한다.
- **G-003. 표준 인증·인가**: 토큰 발급, 사용자 해석, 역할·scope·permission 검사를 재사용 가능한 방식으로 제공해야 한다.
- **G-004. 표준 의존성 접근**: 초기화된 DocMesh 서비스와 서비스 고유 자원에 FastAPI 의존성 주입 방식으로 접근할 수 있어야 한다.
- **G-005. 예측 가능한 운영 상태**: 생존 상태와 준비 상태를 분리하고, 필수 의존성 실패와 선택 의존성 저하를 구분해야 한다.
- **G-006. 안전한 수명주기**: 외부 서비스와 서비스 고유 자원의 생성, 시작 시 점검, 실패 복구 및 종료를 애플리케이션 수명주기 안에서 관리해야 한다.
- **G-007. 추적 가능한 오류 처리**: 모든 HTTP 요청에 안전한 상관관계 식별자를 부여하고, 오류를 일관된 형식으로 반환하되 민감 정보를 노출하지 않아야 한다.
- **G-008. 확장 가능성**: 서비스 팀이 내부 앱 상태 구조를 직접 조작하지 않고 준비 상태 점검, 관리 자원 및 도메인 오류 표현을 확장할 수 있어야 한다.
- **G-009. 앱 간 격리**: 한 프로세스에서 여러 앱을 구성해도 앱별 인증 문서 설정과 런타임 상태가 서로 간섭하지 않아야 한다.
- **G-010. 소비사 회귀 검증**: 소비 서비스가 공통 health, auth opt-in 및 자원 수명주기 계약을 실제 앱 수명주기에서 검증할 수 있어야 한다.
- **G-011. 선언적 자원 계약**: 자원 식별자, 생성·종료, readiness 및 typed dependency를 하나의 선언 경계에서 재사용할 수 있어야 한다.
- **G-012. 일관된 전송 계약**: 도메인 경계가 인증, validation, 공통 오류 응답 및 OpenAPI 정책을 한 번 선언하면 runtime과 문서에 동일하게 반영되어야 한다.
- **G-013. 안전한 응답 수명주기**: streaming 응답이 소유한 자원은 정상·실패·취소·연결 종료 경로에서 누락 없이 정리되어야 한다.

### 2.2 비목표

- 개별 도메인 서비스의 비즈니스 endpoint 또는 domain schema 제공
- UI 또는 프론트엔드 제공
- 외부 시스템의 전체 관리 기능 제공
- 모든 조직의 API·권한·오류 정책을 하나의 고정 형식으로 강제
- DocMesh Py Core가 소유하는 서비스별 연결 설정과 client 구현의 중복 소유

## 3. 제품 요구사항

### 3.1 애플리케이션 조립

- **PR-APP-001**: 서비스 팀은 설정, 사전 조립 runtime, 사용자 lifespan 및 서비스 고유 자원을 선택적으로 결합해 FastAPI 앱을 생성할 수 있어야 한다.
- **PR-APP-002**: 공통 health 기능은 기본 제공하고, 인증 기능은 서비스가 명시적으로 선택할 수 있어야 한다.
- **PR-APP-003**: CORS, 요청 추적 및 표준 오류 처리 정책은 공통 앱 조립 과정에서 일관되게 적용되어야 한다.
- **PR-APP-004**: 기본 앱은 외부 인프라 의존 없이 실행 가능해야 하며, 활성 서비스가 지정된 경우에만 해당 runtime을 조립해야 한다.
- **PR-APP-005**: 서비스 팀은 도메인 router를 앱 생성 입력으로 전달하여 공통 middleware·오류·수명주기 정책과 한 번에 조립할 수 있어야 한다.

### 3.2 인증과 인가

- **PR-AUTH-001**: 서비스는 표준 토큰 발급 및 현재 사용자 조회 기능을 선택적으로 노출할 수 있어야 한다.
- **PR-AUTH-002**: 인증 실패, 인증 시스템 구성 오류, 일시 장애 및 upstream 오류는 운영 의미가 구분되는 응답으로 처리되어야 한다.
- **PR-AUTH-003**: route는 현재 사용자와 역할·scope·permission 검사를 공통 dependency로 재사용할 수 있어야 한다.
- **PR-AUTH-004**: 각 앱은 자신의 인증 문서 설정을 독립적으로 유지해야 한다.
- **PR-AUTH-005**: 인증 기능을 노출하는 앱은 인증 서비스 선택·설정·runtime provider의 불일치를 첫 인증 요청 전에 진단하고, 해결 가능한 구성 오류로 보고해야 한다.
- **PR-AUTH-006**: 서비스 팀은 공통 인증·인가 정책을 route마다 반복하지 않고 module 또는 router 경계에 적용할 수 있어야 하며, health와 token 발급 등 적용 대상이 아닌 공통 endpoint에는 의도치 않게 확산되지 않아야 한다.

### 3.3 서비스와 자원 접근

- **PR-DEP-001**: route는 활성화된 DocMesh 서비스 runtime, 설정 및 서비스별 client를 표준 dependency로 사용할 수 있어야 한다.
- **PR-DEP-002**: 사용할 수 없는 서비스와 잘못 조립된 client 타입은 서로 다른 운영 오류로 식별되어야 한다.
- **PR-DEP-003**: 서비스 팀은 서비스 고유 자원을 선언적으로 등록하고 타입이 명확한 dependency 경로로 접근할 수 있어야 한다.
- **PR-DEP-004**: 공통 기능 사용자는 폐기된 내부 앱 상태나 비공개 client 저장 구조에 의존하지 않아야 한다.
- **PR-DEP-005**: 서비스 고유 자원의 동기·비동기 호출은 event loop 차단과 수명주기 중복 구현 없이 공통 실행 정책을 사용할 수 있어야 한다.

### 3.4 도메인 모듈 조립

- **PR-MOD-001**: 서비스 팀은 관련 router, 관리 자원, readiness 점검 및 도메인 오류 정책을 하나의 재사용 가능한 domain module로 선언할 수 있어야 한다.
- **PR-MOD-002**: 여러 domain module을 조립할 때 이름 또는 등록 대상이 충돌하면 부분 적용 없이 앱 생성이 실패해야 한다.
- **PR-MOD-003**: module은 공통 인증·validation·오류·응답 문서 정책을 module 경계에서 선언할 수 있어야 하며, 해당 정책은 적용 대상 route에만 영향을 주어야 한다.
- **PR-MOD-004**: 여러 module의 전송·오류 정책이 서로 모순되면 silent override 없이 앱 조립 전에 진단되어야 한다.

### 3.5 수명주기와 readiness

- **PR-LIFE-001**: 외부 서비스와 서비스 고유 자원은 정해진 순서로 시작되고 역순으로 종료되어야 한다.
- **PR-LIFE-002**: 부분 초기화 실패 시 이미 생성된 자원은 가능한 범위에서 정리되어야 하며, 정리 실패가 원래 실패를 숨기지 않아야 한다.
- **PR-LIFE-003**: 시작 시 상태 점검은 실패 정책, 재시도, 서비스별 timeout 및 전체 timeout을 지원해야 한다.
- **PR-READY-001**: 준비 상태는 정상, 선택 의존성 저하, 필수 의존성 오류를 구분해야 한다.
- **PR-READY-002**: 필수 의존성 실패가 발생해도 진단 가능한 다른 의존성 결과를 함께 제공해야 한다.
- **PR-READY-003**: 사용자 정의 점검은 동기·비동기 구현, 필수 여부, timeout 및 오류 노출 정책을 지정할 수 있어야 한다.
- **PR-READY-004**: readiness 확장은 공개된 typed 등록 경로를 사용하고 내부 dict/set 상태를 직접 조작하지 않아야 한다.

### 3.6 설정, 오류 및 관측성

- **PR-CFG-001**: 활성 서비스, 필수 서비스 및 대체 서비스 그룹의 모순은 요청 처리 전에 발견되어야 한다.
- **PR-CFG-002**: 앱 계층 설정과 DocMesh 서비스별 설정의 소유 경계가 분명해야 한다.
- **PR-ERR-001**: HTTP, validation, 인증·인가, 미처리 오류는 상관관계 식별자를 포함한 일관된 오류 계약으로 정규화되어야 한다.
- **PR-ERR-002**: 서비스 팀은 도메인 예외를 공통 오류 흐름에 연결하고 필요하면 응답 envelope를 교체할 수 있어야 한다.
- **PR-ERR-003**: 외부 오류 메시지와 로그는 credential, token 등 민감 정보를 노출하지 않아야 한다.
- **PR-ERR-004**: 앱 및 domain module은 여러 도메인 예외 매핑을 선언적으로 제공할 수 있어야 하며, 모든 매핑은 기존의 민감 정보 제거와 공통 오류 rendering 정책을 따라야 한다.
- **PR-ERR-005**: 도메인 예외 매핑은 가장 구체적인 예외 유형과 명시적 fallback을 결정론적으로 선택해야 하며, 중복·도달 불가능한 선언을 조립 시점에 거부해야 한다.
- **PR-ERR-006**: 서비스는 상관관계 ID, 안전한 메시지, status별 code 및 선택적 envelope/Problem Details 형식을 조합 가능한 표준 오류 rendering 정책으로 선택할 수 있어야 한다.
- **PR-OBS-001**: 주요 애플리케이션 경계와 운영 실패는 구조화된 방식으로 기록되어 장애 분석에 활용할 수 있어야 한다.
- **PR-OBS-002**: 모든 HTTP 요청의 완료 결과는 method, route, 상태, 처리 시간 및 상관관계 식별자를 포함하는 안전한 access log로 기본 기록되어야 한다.

### 3.7 소비사 검증

- **PR-TEST-001**: 소비 서비스는 외부 서비스가 없는 canonical runtime으로 앱 계약을 격리 검증할 수 있어야 한다.
- **PR-TEST-002**: 공통 health 기능과 인증 router 포함 여부를 재사용 가능한 assertion으로 확인할 수 있어야 한다.
- **PR-TEST-003**: 관리 자원의 생성·점검·종료 순서를 실제 앱 lifespan에서 검증할 수 있어야 한다.
- **PR-TEST-004**: 테스트는 환경 override와 관련 설정 cache의 초기화·복원을 하나의 격리된 context로 관리할 수 있어야 한다.
- **PR-TEST-005**: 소비 서비스는 domain module이 의도한 앱 기능을 등록했는지와 그 결과 생성된 OpenAPI의 route·security·schema 계약을 재사용 가능한 assertion으로 검증할 수 있어야 한다.
- **PR-TEST-006**: 소비 서비스는 module 이름, 자원·readiness·오류 매핑, transport policy 및 OpenAPI 응답 계약을 하나의 불변 프로필로 검증할 수 있어야 한다.
- **PR-TEST-007**: 계약 검증은 JSON snapshot이 아니라 path·method·status·security scheme·schema reference·operation ID의 의미를 검증해야 한다.

## 4. 달성 조건

### 4.1 필요성 충족

- **DC-001. 중복 개발 부담 해소**: 서비스 팀이 앱 초기화, 공통 보안, 운영 상태, 오류 처리 및 외부 의존성 수명주기를 서비스마다 다시 구현하지 않는다.
- **DC-002. 서비스 간 일관성 확보**: 공통 기능의 적용 방식 차이로 발생하는 보안·운영·장애 분석 품질 편차가 줄어든다.

### 4.2 목적 달성

- **DC-003. FastAPI 컴포넌트 가치 제공**: 제품은 인프라 연결 도구를 넘어 DocMesh Py Core 기반 기능을 웹 서비스로 구성·운영하는 공통 기반이 된다.
- **DC-004. 도메인 개발 집중도 향상**: 개발자는 공통 웹 계층보다 도메인 router와 비즈니스 기능 구현에 집중할 수 있다.

### 4.3 목표 달성

- **DC-005. 안전하고 재사용 가능한 기반**: 인증·인가, 설정·client 접근, 자원 수명주기, 오류 처리와 요청 추적을 공통 방식으로 재사용할 수 있다.
- **DC-006. 예측 가능한 운영 경험**: 운영자는 생존 여부, 정상 준비, 부분 저하 및 필수 의존성 오류를 일관된 기준으로 해석할 수 있다.
- **DC-007. 내부 구조에 독립적인 확장**: 서비스 고유 자원과 readiness 및 도메인 오류를 공개 확장 계약으로 연결할 수 있다.
- **DC-008. 신뢰 가능한 조립과 업그레이드**: 구성 오류와 앱 간 간섭을 기동 전에 줄이고, 소비사 계약 검증으로 버전 업그레이드 회귀를 탐지할 수 있다.

### 4.4 완료 판정

- 각 요구사항은 서비스 개발자 또는 운영자가 체감하는 결과로 설명·검증할 수 있어야 한다.
- 공통 앱 조립, 인증·인가, 서비스·자원 접근, readiness, 수명주기, 오류 추적 및 소비사 계약 검증의 회귀 테스트가 통과해야 한다.
- 구체 인터페이스, 상태 코드, lifecycle 순서 및 검증 항목은 `docs/srs.md`를 기준으로 판정한다.
