# fastapi-core 제품 요구사항 정의서 (PRD)

> 문서 목적: `fastapi-core`를 **DocMesh Py Core 기반 서비스를 FastAPI 환경에서 동작시키기 위한 기능을 제공하는 FastAPI 컴포넌트**로 정의한다.
> 문서 원칙: 이 문서는 capability 중심 PRD이다.

---

## 1. 문서 개요

- 문서명: `fastapi-core 제품 요구사항 정의서`

### 1.1 배경

`fastapi-core`는 단순한 인프라 SDK 문서 묶음이 아니라, **DocMesh Py Core 기반 서비스를 FastAPI 환경에서 구동하기 위해 필요한 기능을 제공하는 공통 FastAPI 컴포넌트**여야 한다.

이 프로젝트의 핵심 가치는 외부 의존성에 연결하는 것 자체보다, DocMesh Py Core 기반 서비스를 FastAPI 애플리케이션으로 구성할 때 반복적으로 필요한 웹 계층 기능과 조립 부담을 줄이는 데 있다. 예를 들면 다음과 같다.

- FastAPI 앱 초기화
- 공통 CORS / 오류 처리 정책 적용
- 공통 인증 및 헬스체크 기능 연결
- 현재 사용자 해석 및 권한 검사 흐름 표준화
- 표준 응답 모델 제공
- startup / shutdown 수명주기와 외부 의존성 연결의 결합
- 운영 readiness 상태를 일관된 방식으로 노출
- 서비스 고유 자원을 공통 lifecycle과 readiness 정책에 연결할 때 내부 앱 상태 구조를 직접 조작해야 하는 부담

### 1.2 문제 정의

- DocMesh Py Core 기반 서비스를 FastAPI 애플리케이션으로 노출할 때 앱 초기화와 middleware / router 조립이 서비스마다 중복될 수 있다.
- 공통 인증 및 헬스체크 엔드포인트의 동작이 서비스별로 달라지면 DocMesh 기반 서비스의 운영 일관성이 낮아질 수 있다.
- `Depends(...)` 기반 인증/설정 dependency가 서비스마다 달라지면 보안과 유지보수 품질이 흔들린다.
- DocMesh Py Core 기능은 공유하더라도, 이를 감싸는 FastAPI 계층이 표준화되지 않으면 실제 서비스 개발 생산성과 운영 일관성은 충분히 올라가지 않는다.

## 2. 목표 / 비목표

### 2.1 목표

- DocMesh Py Core 기반 서비스가 FastAPI 환경에서 일관된 방식으로 구동될 수 있어야 한다.
- FastAPI 서비스가 공통 앱 팩토리 중심의 조립 경로를 사용할 수 있어야 한다.
- 공통 인증 및 헬스체크 라우팅 표면을 재사용 가능해야 한다.
- 설정 접근, 인증 provider 접근, 현재 사용자 해석, 권한 검사를 위한 공통 dependency를 제공해야 한다.
- 서비스가 초기화한 외부 서비스 클라이언트에 FastAPI 의존성 방식으로 접근할 수 있어야 한다.
- 인증 응답, 사용자 정보, 헬스 상태에 대한 표준 응답 모델을 제공해야 한다.
- 설정/인증/메시징/스토리지 같은 인프라 기능이 FastAPI startup/shutdown 및 request lifecycle과 자연스럽게 통합되어야 한다.
- FastAPI 서비스 작성자가 DocMesh Py Core 기반 기능을 웹 서비스로 노출할 때 바로 사용할 수 있는 **웹 애플리케이션 표면**을 제공해야 한다.
- 서비스 고유 자원의 생성, 접근, 상태 점검, 종료를 하나의 선언적 확장 계약으로 구성할 수 있어야 한다.
- readiness 확장은 내부 상태의 dict/set 구조를 알지 않고도 타입이 명확한 등록 경로를 통해 수행할 수 있어야 한다.
- 활성 서비스와 필수 서비스 설정의 모순을 애플리케이션 기동 전에 발견할 수 있어야 한다.
- 한 프로세스에서 여러 앱을 구성해도 각 앱의 인증 문서 설정이 서로 영향을 주지 않아야 한다.
- role, scope, permission 정책을 route에서 문자열 비교 로직으로 반복 구현하지 않아야 한다.
- 모든 요청과 오류 응답을 안전한 correlation ID와 표준 오류 형식으로 추적할 수 있어야 한다.

### 2.2 비목표

- 개별 도메인 서비스의 비즈니스 endpoint 제공
- 서비스별 domain schema 전체 통합
- UI / 프론트엔드 제공
- 각 외부 시스템의 전체 관리자 기능 제공
- 모든 조직의 API 정책을 한 번에 일반화하는 것

## 3. 달성 조건

다음 조건을 모두 충족하고 자동화된 검증으로 재현할 수 있을 때, 본 제품 요구사항을 달성한 것으로 판단한다. 구체적인 인터페이스와 검증 절차는 SRS 및 테스트 문서에서 관리한다.

- **DC-001. 표준 앱 조립**: 서비스 개발자는 공통 앱 조립 경로를 사용해 기본 웹 애플리케이션을 생성하고, 도메인 라우터만 추가하여 서비스를 구성할 수 있어야 한다. 생성된 앱에는 공통 CORS, 오류 처리, 요청 추적 및 운영 상태 확인 기능이 일관되게 적용되어야 한다.
- **DC-002. 인증·인가 재사용**: 서비스 개발자는 공통 dependency를 통해 인증된 사용자, 인증 제공자, 역할·scope·permission 기반 접근 제어를 적용할 수 있어야 하며, 각 라우트에서 토큰 해석이나 문자열 비교 정책을 중복 구현하지 않아야 한다. 인증되지 않았거나 권한이 부족한 요청은 표준 오류 형식으로 안전하게 거부되어야 한다.
- **DC-003. 외부 의존성 수명주기 관리**: 설정된 DocMesh Py Core 기반 외부 의존성 및 서비스 고유 자원은 애플리케이션 시작 시 준비되고, 시작 실패 시 이미 생성된 자원이 정리되며, 정상 종료 시에도 역순으로 정리되어야 한다. 사용자 정의 수명주기와 함께 사용해도 이 정리 보장이 유지되어야 한다.
- **DC-004. 선언적 자원 확장**: 서비스 개발자는 내부 애플리케이션 상태의 자료구조를 직접 조작하지 않고, 타입이 명확한 선언적 등록 경로로 서비스 고유 자원을 생성·접근·상태 점검·종료 처리에 연결할 수 있어야 한다. 중복 이름, 예약 이름, 유효하지 않은 시간 제한은 기동 전에 거부되어야 한다.
- **DC-005. 운영 상태 판별**: 운영자는 공통 상태 확인 표면에서 프로세스 생존 상태와 의존성 준비 상태를 확인할 수 있어야 한다. 필수 의존성 실패는 서비스 불가 상태로, 선택 의존성 실패는 부분 저하 상태로 구분되며, 점검 오류에는 민감한 연결 정보가 노출되지 않아야 한다.
- **DC-006. 기동 전 구성 검증**: 활성화된 서비스, 필수 서비스, 대체 서비스 그룹의 구성 모순은 애플리케이션이 요청을 처리하기 전에 발견되어야 한다. 유효한 구성에서는 선택된 서비스 클라이언트와 설정만 앱 수명주기에 연결되어야 한다.
- **DC-007. 앱 간 격리**: 동일 프로세스에서 여러 FastAPI 애플리케이션을 생성해도 인증 문서 설정, dependency 동작, 상태 및 서비스 런타임이 서로 공유되거나 변경되지 않아야 한다.
- **DC-008. 오류 추적 가능성**: 모든 HTTP 요청은 안전한 correlation ID를 가지며 응답에서 이를 확인할 수 있어야 한다. 검증 오류, 인증 오류 및 처리되지 않은 오류는 일관된 표준 오류 형식과 correlation ID를 제공하고, 내부 예외나 민감한 값은 클라이언트에 노출하지 않아야 한다.

### 3.1 완료 판정

- 각 달성 조건은 단위·통합 테스트에서 정상 경로와 실패 경로로 검증되어야 한다.
- 서비스 개발자가 비목표 범위의 도메인 endpoint, 도메인 schema 또는 외부 시스템별 관리자 기능을 구현하지 않고도 위 조건을 사용할 수 있어야 한다.
- 회귀 검증에서 공통 앱 조립, 인증·인가, readiness, 자원 수명주기, 구성 검증, 오류 응답 및 다중 앱 격리 관련 테스트가 모두 통과해야 한다.
